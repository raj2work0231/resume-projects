Real-Time Kafka Streaming Pipeline (Multiplexer Pattern)

Production pipeline where Databricks consumes multiple Kafka topics and lands raw events as Parquet on ADLS Gen2. A streaming Multiplexer Delta table centralises CDC routing (INSERT / UPDATE / DELETE per target table), then a cost-optimised scheduled batch populates SCD Type 1 and SCD Type 2 downstream tables based on business requirement.

Solution Overview

This pipeline consumes events from multiple Apache Kafka topics via Spark Structured Streaming and lands them as raw Parquet files on ADLS Gen2 — decoupling high-throughput ingestion from transformation overhead. An AutoLoader streaming job then reads these files into a single centralised Multiplexer Delta table, which records the source Kafka topic, target downstream table name, and CDC operation type (INSERT / UPDATE / DELETE) for every message. A metadata-driven routing job runs on a fixed schedule to read unprocessed Multiplexer records and apply either SCD Type 1 or SCD Type 2 MERGE into the appropriate downstream table as defined in the topic routing config — decoupling streaming ingestion from batch transformation to control compute cost.

Pipeline Stage Details

Stage 1 — Raw Parquet Landing (ADLS Gen2)

Databricks Structured Streaming consumes from Kafka and writes raw events to ADLS Gen2 as Parquet files, partitioned by topic and ingest date. No Delta transformation overhead at this stage — optimised purely for throughput.

format("parquet") Partitioned by topic / ingest_date Kafka metadata preserved Checkpoint per topic maxOffsetsPerTrigger throttle Dead-letter quarantine

Stage 2 — Multiplexer Delta Table (Streaming Load)

AutoLoader streams from the Parquet landing zone into a single centralised Multiplexer Delta table. Each record is enriched with: source Kafka topic, target downstream table (from routing config), and CDC operation type (INSERT / UPDATE / DELETE extracted from payload). Acts as a universal message router for all topics.

AutoLoader cloudFiles kafka_topic column target_table column operation: I / U / D business_key (JSON) processed_flag for routing Append-only streaming

Stage 3 — Downstream Tables (Scheduled Batch)

A routing job runs on a fixed schedule (to control compute cost) and reads unprocessed Multiplexer records. For each target_table, it looks up the scd_type from the routing config and applies either SCD Type 1 (latest wins) or SCD Type 2 (full history with eff_from / eff_to) MERGE INTO the downstream Delta table.

SCD Type 1 — latest-wins MERGE SCD Type 2 — eff_from / eff_to / crnt_flag Routing driven by scd_type config Fixed schedule (cost optimised) processed_flag updated post-merge MD5 row hash change detection

Metadata-Driven Routing Framework

A single topic_routing config Delta table drives the entire pipeline. Adding a new Kafka topic requires only a row insert — no code deployment. The scd_type column determines whether the downstream table uses SCD1 (latest-wins) or SCD2 (full audit history):

Impact & Outcomes

  • Decoupled high-throughput streaming ingestion (Kafka → Parquet) from transformation cost
  • Multiplexer pattern enables a single streaming job to serve all Kafka topics via a central routing table
  • Fixed-schedule batch routing reduces compute spend vs always-on streaming transformation
  • Metadata-driven design — onboarding a new Kafka topic requires only a row insert in the routing config
  • SCD type (1 or 2) is business-requirement driven per downstream table, not hardcoded by layer
  • Idempotent processing via processed_flag and Delta MERGE ensures no duplicate downstream records
